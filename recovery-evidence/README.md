# LaminaDB 恢复证据包

本包重建一个具体事实：**恢复后的数据库状态等于"备份/检查点捕获的提交前缀"与"日志追赶后缀"拼接而成的哪一个提交前缀**，并用独立于内核三条通道（客户端模型、日志字节、镜像字节）核对恢复主张是否成立。证据不是启动日志的摘录：所有状态都由驱动程序对**未修改的原版内核**实际运行产生，故障全部从进程外注入（SIGKILL、文件追加、副本字节翻转）。

- 运行时间：2026-11-18T04:40:37Z（UTC），全程约 1.25 秒
- 内核基线：git `cb08bd0ed7adf4df8e4a080db7ddcdc2f7a9cd42`（未做任何修改）
- 被测二进制：`bin/laminad`，SHA-256 `dcc0877885375c0275f6e79da0ac8ef174997ef952d8161d77b9b66e817df0c9`，9,994,802 字节（go1.27.4 linux/arm64 构建；哈希对 GOROOT 路径敏感，见 §10）
- 结果：7/7 条恢复主张 **verified**（`evidence/claims.json`）

## 2. 要重建的事实

LaminaDB 的恢复有两条拓扑，本包对两条都给出"前缀 = 镜像段 + 日志段"的确切序号边界：

- **拓扑 1（原地检查点）**：`checkpoint.lmi` 冻结 `[1..C]`，恢复 = 镜像 `[1..C]` + 日志后缀 `[C+1..H]`。
- **拓扑 2（便携备份还原）**：`backup.lmi` 冻结 `[1..B]`，还原实例的日志从 `base=B` 重新起头，恢复 = 备份镜像 `[1..B]` + 还原实例自己的日志 `[B+1..K]`。**源库在备份点之后的提交不属于还原前缀**；还原后同一序号是另一支历史（§6）。

## 3. 方法与独立核对通道

每条恢复主张都由三条独立通道交叉核对，任何单一通道都不被当作结论：

1. **客户端独立模型**：驱动只根据"已收到 200+sequence 的提交"维护期望行集（未确认提交单独记账），恢复后全行比对 `/query`。
2. **日志字节独立解码**：驱动用 Python 直接解析 `journal.lmw`（16 字节头 + 长度/CRC32 帧 + JSON 记录），产出帧表（偏移、长度、CRC、序号、类型、变更键，不含行负载），验证序号从 base+1 起连续、与客户端确认的提交一一对应。
3. **镜像字节独立解码**：直接解码 `checkpoint.lmi`/`backup.lmi` 信封（按原始 payload 字节重算 SHA-256），重建镜像内版本链在 `image.sequence` 处的可见行，与 API 行、客户端模型三方一致。

行数据核对不是"再查一次库"：模型来自驱动自己的记账，日志/镜像来自文件字节，API 来自内核服务——三者来源独立。

## 4. 实际运行出的状态

### 4.1 确认响应的提交（必须耐久）

时序：DDL(seq 1) 后，4 个提交依次收到 200（seq 2,3,4,5，t=53–71ms）。随后经历 **3 次 SIGKILL 崩溃 + 重启**（§4.2）和一次优雅重启，最终恢复态与独立模型逐行一致（`api/rows-checkpoint-journal-suffix.json`，`match=true`）。日志帧表显示 seq 1..9 连续无缺口（`journal-tables/A-journal-final.json`）。

### 4.2 未确认但可能耐久的提交（三个实例，两种结局）

用裸 socket 发出提交、**不消费响应**即 SIGKILL，崩溃瞬间客户端无法判定结局；真相只能由恢复核验给出：

| 实例 | 写集 | 杀死时机 | 崩溃时客户端所知 | 恢复后真相 |
| --- | --- | --- | --- | --- |
| A0 | 1000 行（写集上限） | 发送后立即 | 无响应（0 字节） | **丢失**：0/1000 行落盘，seq 停在 5，无撕裂尾；写集全有或全无 |
| A | 1 行（sample=7） | 发送后立即 | 无响应（0 字节） | **丢失**：0/1 行，seq 停在 5 |
| B | 1 行（sample=8） | 发送后 60ms | 响应未消费（杀死后才读到 200 字节在途响应） | **耐久**：seq 6，行在 |

在途响应原文保留在 `excerpts/ambiguous-remnant-B-kill-after-60ms-unconsumed-response.txt`：`HTTP/1.1 200 OK … {"sequence":6,"writes":1}`。它证明"服务器已确认"与"客户端已确认"可以分离——**没有收到响应 ≠ 没有耐久**（实例 B），**发了提交 ≠ 已经耐久**（实例 A0/A）。基线文档"调用方可能无法确定该次提交最终是否落盘，应重启后核对实际状态"由此得到运行级证据。注意实例 A 的结局是时序相关的：另一次运行中同样参数的小提交曾耐久（§10.3）。

### 4.3 不完整尾部（截断）

复制源数据目录，向 `journal.lmw` 追加 3 字节（`excerpts/tail-append-before-after.txt` 留有追加前后末 32/35 字节 hex）。重启后：`recovered_tail_bytes=3`，head 不变（seq 9），行集与追加前逐行一致（`api/s6-stats-tail-recovered.json`、`api/rows-tail-truncation.json`）。截断后日志被独立重解码：9 帧完好、无尾部残留。追加态（尚未截断）的完整哈希留在 manifest（`A-tail-journal-with-3-byte-tail-before-restart`），保管链不断。

### 4.4 完整损坏（拒绝，不默默截断）

两份日志副本分别做单比特翻转：**末帧负载最后一字节**、**首帧（DDL）负载中部**。两次启动均退出码 1、stderr 含 `journal checksum mismatch at <offset>`，且**拒绝后日志文件哈希与翻转后一致**——内核没有默默截断或改写（`api/s6-corrupt-last-frame-startup.json`、`api/s6-corrupt-mid-frame-startup.json`，`journal_unmodified_after_refusal=true`）。完整帧 CRC 错误与不完整尾部由此区分开：前者整体拒绝，后者仅截断最后一帧。

## 5. 核心事实：前缀的组成

**拓扑 1（原地）**：`checkpoint` 在 seq 7 捕获镜像（独立解码：`image.sequence=7`，payload 摘要一致）。恢复 = 镜像 `[1..7]` + 日志帧 `[8..9]` = 提交前缀 `[1..9]`，与 head 一致；在 seq 7 的时光查询与模型在 seq 7 的快照一致（`time-travel-at-checkpoint match=true`）。日志保留全部 9 帧（不截短），重放只应用 `>7` 的帧。

**拓扑 2（便携还原）**：备份在 seq 8 捕获（信封摘要独立重算一致，`image.sequence=8`）。此后源库又提交 seq 9（sample=11）。还原实例：

- 行集 == 模型在 seq 8 的快照（**不含 sample=11**，`post-backup-commit-absent row11_absent=true`）；
- 还原日志头 16 字节：`LMW1` + `base=8` + CRC 有效（`excerpts/R-journal-header.txt`）；
- 还原实例新提交 sample=12 得 seq 9，重启后恢复 = 备份 `[1..8]` + 自有日志 `[9]` = **还原前缀 `[1..9]`（新世系）**，与源库前缀 `[1..9]` 同号不同内容。

结论：**"备份捕获 + 日志追赶"组成的提交前缀，边界由镜像内 `sequence`（= 日志头 base）唯一确定；镜像覆盖 `[1..base]`，日志覆盖 `(base..head]`，两者序号相接无重叠无缺口**。还原场景下源库备份点之后的日志不属于该前缀。

## 6. 还原后的变更游标缺口（不能用当前值相同掩盖）

- 旧游标被拒：还原实例 `GET /changes?after=3` → **410** `{"error":{"code":"snapshot","message":"change history begins at 8"}}`（`api/s4-changes-old-cursor-410.json`），`history_base=8`。
- **掩盖陷阱实证**：源库在 seq 4、5 把 sample=2 的 amplitude 20→200→20。游标 3 处的消费者最后所见值是 20，还原实例当前值也是 20——若用"当前值相同"判断是否同步，会得出"无缺口"的错误结论；实际上两次已提交的变更永远不可达（410）。当前值相同不代表变更历史连续。
- **同号不同世系**：源库 seq 9 记录 tx `49171061…`（写 sample=11），还原实例 seq 9 记录 tx `75c3db86…`（写 sample=12）（`api/s3-changes-after-backup-seq-source.json` vs `api/s4-changes-after-base-restored.json`）。游标等于 base 时接口返回 200 并沿**新世系**继续——410 只保护 base 之下的游标，base 处的游标会静默接到另一支历史。变更消费者在还原边界后必须重新对齐基线（全量重载或比对首条记录内容），不能沿用旧游标，也不能用当前值核对代替变更流。

## 10. 无法判定项与补证代价

1. **物理介质耐久性**：fsync 返回成功不等于字节已落物理介质（可能在盘缓存）。用户态无法判定。补证：断电注入台架 / 块层追踪（blktrace）+ 突然断电重放；代价为专用硬件与数人日，超出本包范围。
2. **丢失提交的确切死亡点**：A0/A 提交丢失且 `recovered_tail_bytes=0`，可知死于日志写完成之前，但无法区分"未进入 write()"与"write 途中被杀且未留部分帧"。补证：对写路径做 ptrace/eBPF 观测；代价为引入内核态追踪工具，且仍是概率性定位。
3. **实例 A 结局的分布**：小提交立即杀的结局时序相关（本轮丢失，另一轮曾耐久）。单次运行不能给出概率。补证：同场景重复 N 次统计分布；代价为机时，且结论仅对本机负载/存储有效。
4. **在途响应的应用语义**：实例 B 证明服务器已发出 200；真实客户端"若不死是否会处理该响应"取决于其自身实现，数据库侧无法补证。
5. **行级核对的全量性**：本包对小数据量做了全行比对。生产规模下全量比价为 O(数据集)；可降级为计数+有序键哈希+抽样，代价是核对完备性下降。
6. **有机撕裂尾未出现**：本轮 3 次 SIGKILL 的 `recovered_tail_bytes` 均为 0（另在场景开发期的一次 8 连杀探针中亦为 0），撕裂尾仅以合成追加演示。补证：大量崩溃迭代或存储层故障注入以捕获有机部分帧；代价高且非确定。

## 11. 证据留存策略（可审计范围 vs 保存成本）

| 类别 | 内容 | 体量 | 理由 |
| --- | --- | --- | --- |
| raw | 小型 API 捕获：提交/检查点/统计响应、410 体、变更页、各恢复点全行快照 | 见 `manifest.json`（raw 合计约 30 KB 中的大部分） | 恢复主张的直接对象，体积小，全留 |
| excerpt | 有界 hex：日志头 16B、尾部追加前后 32/35B、翻转点 ±16B、备份信封头 160B、在途响应 200B | 每份 ≤ 数百字节 | 证明字节级状态（base、撕裂位置、翻转位置）而无需保留整个文件 |
| derived | 日志帧表（偏移/长度/CRC/序号/类型/变更键，**不含行负载**）、镜像独立解码结论 | 每份数 KB | 承载"前缀"事实本身：序号连续性与组成边界 |
| hash-only | 完整日志、检查点/备份镜像、服务器 stderr 日志、追加后未截断的日志态 | 仅 SHA-256+尺寸（被引对象合计约 19.6 KB） | 大对象只钉哈希；内容可由 `reproduce.sh` 重导（结构级） |
| 不保留 | 完整数据目录 | — | 约 1.3 秒可重建 |

本次留存合计 **30,658 字节**（49 个 manifest 条目），被哈希钉住但不留内容的对象合计 19,567 字节。权衡逻辑：前缀事实由序号/类型/键（帧表）、镜像摘要与序号、API 行快照承载——全部保留；批量字节只增加存储成本，其哈希 + 确定性驱动已能约束。**注意**：因事务 ID 随机，hash-only 对象不可按字节复现，只能按结构复现并重新验证主张；本包哈希钉住的是本次运行的现场。
